# 酒迹 · 双层标签系统设计草案

状态：PD-013/014/015/016 已确认双层标签、酒吧分类、双向投票及自愿到访佐证方向；核验标准、权重、词库、字段枚举与技术实现仍待设计。本文不代表功能已上线。

## 目标

将「能够核实的对象属性」与「用户体验形成的主观印象」严格区分。酒款与酒吧可以共享审核基础设施，但展示层面采用不同分类。**酒吧客观属性走结构化筛选字段，酒吧体验标签限定为「氛围与风格」「适合的场景」两大类（PD-014）。**

| 类型 | 酒款例子 | 酒吧例子 | 发布依据 |
| --- | --- | --- | --- |
| 客观属性 | 配方使用金酒、采用摇和技法 | 是否有露台、是否提供无酒精选项 | 配方记录、可信资料或其他可核验证据 |
| 主观体验 | 清爽、偏酸、适合入门 | 适合约会、安静、适合独饮 | 登录用户真实体验、适当样本及风险审核 |

本表仅用于说明事实与主观体验区别；**酒吧的露台/无酒精选项不应以用户投票的主观标签呈现**，而应作为结构化、来源可追踪的筛选字段。酒款标签词库还未确定。

## PD-014 · 酒吧主观体验标签与事实筛选

| 前端用途 | 用户确认的类别 | 数据来源/治理原则 |
| --- | --- | --- |
| 体验标签 | 氛围与风格 | 社区意见与体验反馈，保留样本量、投票情况及申诉途径 |
| 体验标签 | 适合的场景 | 社区意见与体验反馈，明确为主观共识而非客观事实 |
| 结构化筛选 | 酒吧类型 | 经核实的业态资料，支持多类型与未知状态 |
| 结构化筛选 | 酒水与特色供应 | 菜单/商家信息及经审核的用户纠错，标明更新时间 |
| 结构化筛选 | 环境与设施 | 如露台、包厢、户外座位，基于可核实事实 |
| 结构化筛选 | 价格与消费 | 价格区间、最低消费、优惠时段；需统一口径 |
| 结构化筛选 | 服务与活动 | 预约、演出、宠物友好等，随时间更新 |
| 结构化筛选（新增） | **是否禁烟** | 核实区域与规则，不能将未知当作允许吸烟/禁烟 |

**禁烟字段设计建议，尚待确认：**使用可空的 `smoking_policy` 枚举或具备更细粒度区域字段，而非只用无法表达分区政策的布尔值。候选值如 `smoke_free`、`smoking_allowed`、`designated_area_only`、`unknown`；可附 `policy_scope`（室内/室外）、`verified_at`、`source`。不能凭推测填充数据；遇到当地法定禁烟要求也不能只依商家宣称认定合规。

**酒吧页面建议：**将「筛选条件」与「氛围/场景标签」分开呈现，允许跨组组合条件。没有事实来源或数据不全时提供「未知/待核实」而不是错误的二选一。对于用户提交的事实纠错使用 PD-004 的可审核申请，而不是将「有露台」变成投票标签。

**仍待细化：**体验标签词库、社区投票计分/可信度、事实筛选字段完整枚举、价格/设施的数据来源和搜索交互，不能视为已定。

## PD-015～PD-016 · 双向投票和到访佐证

**已确认投票机制**
- 氛围与场景两类酒吧标签支持「符合／不符合」双向投票。普通登录用户都可以参与，未提供到访证明仍有资格；游客只浏览。
- 以「用户 ID × 酒吧 ID × 标签 ID」去重，只有一条当前有效票。可改票、撤回，保留审计历史。体验投票不能直接核定价格、禁烟和设施等事实。
- 显示有效赞成/反对人数与样本量；若将来实施证据加权，需要同时显示原始计数、可信佐证覆盖情况和计算说明，避免将少数意见包装成总体共识。

**到访可信度（自愿）**
- 支持多种可选佐证方向：临时定位签到、探店图文或现场照片、经用户同意提供的消费凭证；可多种组合，具体可采信条件、核验等级与权重尚未确认。
- 定位接近、图片存在或提供账单均不保证真实到访，AI 只用于可疑行为提示和初审；争议升级人工。到访佐证缺失不等于评价造假。
- 最小必要收集，禁止强制后台持续定位；凭证可脱敏、限制访问与保留期限，公共标签结果不能透露个人位置、订单细节或作者匿名评价身份。
- 禁止商家刷票、诱导好评、购买标签；合理差评及体验分歧受保护。

建议将 `tag_votes` 与可选 `visit_evidence` 记录分离，避免删除到访证据时错误删除合法的用户体验票，证据失效只应影响可信度标记，聚合口径相应重算。

```text
tag_votes(id, assignment_id, user_id, stance, moderation_status,
          created_at, updated_at)
visit_evidence(id, user_id, bar_id, method, review_status,
               verified_at, expires_at, private_media_ref)
vote_visit_evidence(vote_id, evidence_id, linked_at)
```

注意：这是后续数据设计提案，未定义法定证据标准或实际数据库表，不是已完成实现。

## 社区标签工作流

1. 登录用户选择对象并发起添加、修订、撤回或新增标签建议；客观属性须鼓励提交可核实依据，体验标签须清楚标为主观评价。
2. 由 AI 辅助完成规则校验、敏感内容检测、相似标签建议、异常行为提示及审核分流；不让模型仅凭猜测批准事实属性。
3. 对低风险且符合自动通过规则的建议按分层策略处理，证据不足则保持「待核实」；争议、低置信度或高影响事项交人工。
4. 已登录用户对适用的体验标签提交符合/不符合反馈，可以修改与撤回。可信到访可增进参考价值但不能成为强制门槛；防止机器刷票并分别披露原始票数、样本量及可信信息。对客观事实存在争议时以证据核验为主，不靠投票决定事实。
5. 审核决定和标签变更记录主体、依据、版本、时间及申诉/回退历史；管理员可以推翻 AI 结果，并解释原因。

## 数据结构建议（未实施）

```text
tag_definitions(id, domain, layer, category, slug, display_name, aliases, status)
tag_assignments(id, entity_type, entity_id, tag_id, provenance, evidence_ref,
                verification_status, created_by, reviewed_by, updated_at)
tag_votes(id, assignment_id, user_id, stance, created_at, updated_at)
tag_change_requests(id, entity_type, entity_id, tag_id, action, evidence_ref,
                    requester_id, moderation_status, reviewed_by)
tag_audit_log(id, action, actor_kind, actor_id, target_id, rationale, created_at)
```

- domain区分酒款和酒吧，不允许不受控地将不同实体标签混用；有配方版本差异时需保留明确归属，不将某一作者的版本材料自动断言为全部酒款都使用。
- layer 分为 `objective` 和 `subjective`；客观属性可能随时间变更，须支持重新核实。
- provenance 和 verification_status 分离「官方/作者/商家声明」「平台核实」「社区体验」等来源；客观属性不因投票数高而自动转换为已核实。
- 投票去重、权重、最低样本量、可信度、删除/更新政策应先确定规则后再实现。

## 与既有决策的关系

PD-003：投票、提议和更改须登录，游客只能查看公开标签。

PD-004：AI 初审与人工复核；投诉、申诉及治理日志共用平台能力。

PD-005：付费推广不得购买事实属性标签或改变用户体验共识。

PD-007/008/014：酒吧主观体验标签用于地图筛选和推荐；酒吧类型、供应、设施、价格、服务及禁烟政策是另外的结构化筛选字段。不得把主观标签当作客观事实，或让广告影响可信度。

PD-010/011/012：酒款标签用于调酒筛选和推荐；配方版本的用料、操作与评分仍按实际版本处理。
