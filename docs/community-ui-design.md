# 酒迹 · 社区瀑布流与全局发布入口设计

> 状态：**界面及创作入口、打卡默认公开规则已获确认；快速打分发布方式与首版范围待定；尚未实现或验收**。2026-10-16 讨论确认；与 PD-003/004/009/016/019～021 相关。实际 1.0 必须项待 PD-027 决定。

## 1. 社区首页：小红书风格的并列式卡片

- **移动端 / 微信小程序**：社区内容默认**两列瀑布流（masonry）**，不是单列文字列表，也不是所有卡片高度相等的传统宫格。
- **平板 / 较宽窗口**：根据容器宽度与可读卡片宽度调整为**三列**。
- **桌面 / 更宽窗口**：可调整为**四列**；限制内容最大宽度与卡片最大宽度，避免卡片极宽或出现巨大空隙。实际断点由真机与响应式测试确定，而非强行按设备名称划分。
- **卡片主体**：内容封面图（按原始比例合理裁切/留白，并限制极端长宽比）、最多两行标题、作者头像与昵称、点赞等关键互动信息。商业推广必须显著标注；没有封面图的文字帖也有可识别的占位呈现。
- **交互**：轻触卡片进入帖子详情浏览全文、全部图片、酒吧关联、评论和互动；社区主页不展开长篇正文。支持懒加载、翻页/连续加载、骨架屏和加载失败重试，避免图片未加载造成布局明显跳动。
- **页面布局**：顶部保留搜索、筛选/推荐/关注等实际已实现的能力；卡片间距与留白维持“城市编辑”视觉系统，但采用小红书式**信息密度与内容发现方式**，不复制第三方品牌素材和专有视觉资产。
- **入口范围**：所有平台尽量遵循统一的信息结构与卡片规则；尺寸、输入方式、底部安全区按微信小程序、iOS/Android、鸿蒙及大屏网页分别适配。是否支持独立网页端仍属平台规划，不因响应式描述而视为已上线。

## 2. 底部导航：四个栏目 + 中央「＋」

目标结构：

```text
   地图       调酒        ＋        社区       我的
  （Tab）    （Tab）   （发布）    （Tab）    （Tab）
```

- 原有的四个页面标签 **地图、调酒、社区、我的**保持语义及切换能力；中央「＋」是全局**操作按钮**，不是第五个选中态页面标签，也不应让用户误以为切换了栏目。
- 「＋」在四个主要页面均可见，位于视觉正中，点击打开底部操作面板 / 发布菜单；选择取消时回到原页面与原滚动位置。
- **已认可的「＋」五项创作入口**（以统一发布面板呈现，具体版式后续定稿）：
  1. **打卡酒吧**：记录一次到访/想补记的到访记录，可选附近酒吧或搜索酒吧，并可继续拍照与填快速评分；不等同于公开评价或自动确认真实到访。
  2. **写酒吧评价**：选择酒吧或承接当前酒吧上下文，填写总体星级、可选分项与文字/照片，并选择公开昵称或匿名身份；受 PD-019 一人同店仅最新有效评分的规则约束。
  3. **发布图文笔记**：上传图文、标题、话题、可选关联酒吧，按用户明确选择与探店体验/酒吧评价绑定，不默认重复发表或重复计分。
  4. **分享调酒作品**：进入已有调酒模块的配方/成品发布编辑器；从「调酒」模块和「＋」进入同一份草稿与同一提交流程，避免重复业务对象。
  5. **推荐新酒吧**：从地图中找不到目标地点时提交新酒吧线索及证据，进入 PD-004 的审核队列，不自动变成已核实的酒吧或地图点位。
- **不额外占按钮**：「想去／标记好去处」属于地图与酒吧详情的收藏或想去状态（登录后使用），不与打卡混为一谈；**AI 创作灵感**属于笔记和调酒作品编辑器内的可选辅助工具，作为后续能力规划，须由用户检查、修改并主动发布，不能 AI 自动发布。
- **建议开发顺序，尚未确认为 1.0 必交付**：优先打通附近/搜索打卡、快速评价、图文笔记和基础调酒作品发布；推荐新酒吧复用既定酒吧投稿；一键补打卡、相机水印、完整 AI 创作辅助可以后续增强。最终是否为首版阻塞项仍由 PD-027 决定。
- **对某个帖子的评论/回复**需要明确评论对象，应在该帖子详情页发出；不能从无上下文的全局「＋」创建“悬空评论”。如果用户口中的“发评论”实际是指“评价酒吧”，用以上“评价酒吧”入口承接。
- 未登录时点击需要写入的操作先走登录；发布前显示可见性、审核/社区规范等必要提示。对于**匿名酒吧评价与公开署名探店帖**的关联，不得默认公开关联或泄露作者身份，遵循 PD-021。
- 技术实现需考虑微信原生 tabBar 的结构限制：可以保持四个真实 Tab，另行实现安全区适配的中置悬浮操作入口或使用可控的自定义 TabBar；不可因为视觉有五个按钮而把发布页注册成普通 Tab。
- 评价与帖子分别存储、可选关联，绝不因关联或在不同入口展示而重复计入酒吧总评分（PD-019/020）。

## 3. 打卡酒吧的业务流（基于用户演示的产品建议，部分规则待确认）

**打卡入口 → 选择酒吧 → 可选拍照/快速评分 → 完成打卡（默认公开打卡动态）→ 可继续写详细评价**。公开的是「打卡动态」，不等同于公开「酒吧评价」，也不会仅因打卡而计入酒吧星级。

1. **选择目标酒吧**：附近列表（在用户主动授权定位并符合平台权限时展示）、搜索具体地点、浏览已存在的足迹；不应声称后台能够自动知道用户实际去过哪家店。拒绝定位时仍可通过搜索完成非定位打卡/补记。
2. **到店与补记分开**：用户处于允许打卡的地理范围内时，可以发起定位签到；超出范围的店不授予「定位证实」状态，但仍可手动补记曾经到访。过去到访时间由用户自述，不伪装成实时定位核验。
3. **打卡后拍照**：可选上传现场照片，未来可以启用带场所、时间等字段的可选择水印相机；水印本身不是到访真伪证明，尤其不得强制公开精确地理位置。
4. **快速打星**：打卡时可选 1～5 星，但**快速打星究竟是默认草稿、自动发布独立评价，还是单独询问用户，尚未决定**；无论哪种方案，不能把打卡动态本身当成一条有效评分。仅经独立评价流程明确发布且审核有效的星级才按 PD-017～019 计分。
5. **完成打卡的下一步**：保留「稍后写详细评价」或「立即补充评价」的延续路径；打卡记录本身、评价草稿和社区帖子分别建模，可按用户选择关联，同一用户反复到访不会让历史打卡变成多条评分。
6. **足迹与可信度**：打卡历史可以构成个人酒吧足迹；普通手动打卡、定位接近、有照片、有消费凭证属于不同可信证据等级。用户可以不提交证据并继续参与评价与标签投票，不把照片或签到推断为已经核实到访。
7. **公开边界已确认：选择 B，默认公开打卡动态**。点击「完成」将默认产生一条与所选酒吧关联的公开打卡动态；在提交前明确显示该可见性，建议提供「仅自己可见」覆盖选项供用户切换。**不得自动公开精确经纬度、消费凭证或未经用户选定的照片**。打卡公开与评价是否公开/是否计分必须分开处理；匿名评价不得通过公开足迹或署名打卡动态反向关联至作者。

**待设计/实施字段（建议，不是已实现表）：** `bar_checkins(id, user_id, bar_id, asserted_visited_at, created_at, location_verification_status, visibility, media_refs, linked_review_draft_id)`。后续优先考虑复用 `bar_visits` 体验实体，避免签到与探店记录双重计数。定位范围阈值、历史补卡限制、可信度来源及照片保留规则需另议。

## 4. 建议的体验验收项（尚未通过）

1. 在手机视口社区首页展示两列并列卡片、长短卡错落排列；中大屏分别合理过渡至三/四列，不重叠、不横向溢出。
2. 图片加载失败、无图、长标题、广告帖及很长图片比例时仍可阅读；滚动流畅、分页状态正确。
3. 从任何主要 Tab 点击中央「＋」，都能看到“打卡酒吧、写酒吧评价、发布图文笔记、分享调酒作品、推荐新酒吧”；取消后保留原 Tab 状态。
4. 从评价入口独立发布不自动产生公开帖子；从图文入口发布可选择是否关联评价，且不会产生重复计分。
5. 在帖子详情进行评论、回复；未登录状态、匿名关联风险、审核失败/草稿恢复的提示正确。
6. 微信底部安全区、iPhone Home Indicator、Android 导航区域及横竖屏等场景不存在误触或遮挡。
7. 打卡附近列表仅在授权定位后出现；拒绝权限可搜索补记；越过定位范围不能伪造已验证到访；完成打卡默认公开独立动态，但不自动视为有效评分，且不触发匿名评价身份泄露。
8. 调酒分享与调酒模块入口进入同一编辑器，新增酒吧经审核才显示在地图；“想去”与已到访足迹不会混淆。

## 5. 未决细节与边界

- 卡片封面具体圆角、间距、瀑布流排列策略、是否展示浏览量，以及「＋」浮起高度，可根据用户提供的参考截图再微调。
- **用户已确认设计方向，不等于代码已经修改。** 当前 React 微信社区页仍是表单 + 纵向条目；需要另建前端开发任务并完成跨端实现。
- **已确认打卡默认公开，未决快速打星的发布方式**：是否自动成为有效评价、保存草稿，或弹出二次选择，留待下一问。发布前的隐私切换、实时签到与历史补记的展示区别，一键补打卡、拍照水印与近场核验阈值仍需设计。
- 是否把完整瀑布流、统一发布入口、打卡首版列为 1.0 必须项，由下一轮 PD-027 首版优先级讨论决定。
