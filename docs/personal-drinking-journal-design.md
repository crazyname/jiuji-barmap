# 酒迹 · 个人饮酒记录与产品方向重审

> 记录日期：2026-10-17。性质：**需求访谈决策与交互草案**，不是已实现功能，也不是已确定的 1.0 上线范围。
>
> **优先原则：个人记录是基础，社区分享由用户主动选择。** 本文是 2026-10-17 对个人记录体验的最新决策依据。与早期「打卡默认公开／快速星级自动提交公开评价」冲突时，先按本文的隐私原则处理**个人饮酒记录**，旧版打卡公开／评分联动细节标为待重新审议，不可未经重新确认直接开发。

## 一、定位与设计原则

- 酒迹面向饮酒体验、酒吧探索、鸡尾酒查询与调制、个人记录和酒友交流等真实使用场景；不以广告、商家运营、榜单或内容流量作为普通用户体验的默认驱动力。
- 用户可以只记录自己的饮酒经历，不必公开发帖、评分、经营社交账号，也不必先选择酒吧。
- 私人记录默认仅自己可见；进入社区需要明确、独立的分享操作。浏览私人的「我的」页面与其他人访问公开个人主页必须做权限隔离。
- 用户明确希望重新梳理原有范围：社交、排行榜、商家商业化等历史产品决定**并非一概撤销**，但应按以上方向重新审查必要性、默认行为与上线优先级。
- 品牌对外称呼与标语另行确定；本文仅使用产品名称「酒迹」。

## 二、逐项问答确认（本轮新决策，记录为 JR-001～JR-008，避免占用 PD-027）

| 编号 | 访谈问题 / 使用场景 | 选择 | 用户确认的决策 |
| --- | --- | --- | --- |
| JR-001 | 产品以个人记录还是社区分享为主？ | 确认推荐方向 | **个人饮酒记录为基础；公开分享到社区完全由用户自主选择。** |
| JR-002 | 一次饮酒与一次探店是什么关系？ | C | **每杯酒与每次探店都可独立记录、互相关联**；一次探店可以对应多杯酒，家中调酒无需创建探店。默认私人保存。 |
| JR-003 | 记录一杯酒需要填写多少信息？ | C | **快速记录，可随时补充完善**。先保存最少信息，再添加照片、感受、风味、地点、评分、配方等，不强迫一次写完。 |
| JR-004 | 怎样回顾自己的记录？ | D | **个人饮酒时间轴优先**；日历、照片墙，以及按酒款／酒吧筛选逐步增加。 |
| JR-005 | 多次喝过同款酒怎样保存？ | C | **每次饮用保留独立记录，按同款酒归入个人酒款档案**；不同酒吧与家中调制的体验不被覆盖或合并为同一次。 |
| JR-006 | 与鸡尾酒知识库怎样关联？ | C | **输入酒名推荐现有酒款及配方版本，同时允许自由创建私人记录**；缺失知识库条目不阻止记录，可日后关联；不会自动向公共知识库投稿。 |
| JR-007 | 酒吧、在家调酒、其他场景是否要不同表单？ | C | **统一基础字段 + 按场景显示可选专属字段**，不强制填写所有细节。 |
| JR-008 | 一次探店喝多杯，如何操作？ | C | **既可先建一次探店并连续添加多杯，也可先单杯记录、以后关联到某次探店**；不强制创建探店，不按同一天自动合并。 |

上述决策是对同一用户体验的连续讨论；不应把推荐选项外延为未经用户确认的运营目标、技术栈实现或 1.0 必交付承诺。

## 三、记录结构与体验边界

### 1. 一杯酒的「饮用记录」

- 每次饮用是一条独立事实／体验记录；可以先选择知识库中的酒款／配方版本，也可以只输入用户自己的名称。
- 快速记录可先保存极少信息；酒名或知识库选择是已讨论的便捷路径，其他字段与「保存最少必填规则」仍需细化。
- 日期、照片、个人感受、风味、个人评分等可随时补充；不强迫用户先评级，也**不把个人主观记录自动转换成对酒吧的公开评价**。
- 同款酒在不同地点、不同时间、不同版本的饮用记录互相独立；个人酒款档案是聚合视图，不覆盖历史原始记录。
- 对不确定名称或原创特调，可保持「未关联公共酒款」状态；仅在用户主动确认后关联知识库，不因自由输入而新增公众酒款。

### 2. 一次「探店／饮酒经历」

- 一次探店可以独立存在且暂时不含具体酒款；一杯酒也能独立存在且不必关联探店。
- 支持两种起点：
  1. 从酒吧／探店入口创建一次经历，在其中连续添加多杯饮用记录。
  2. 从单杯入口直接保存，稍后将若干已有饮用记录归到某一次经历。
- 关联应由用户主动操作；**相同日期、相同酒吧不代表系统可以自动合并为同一次探店**。
- 同一家酒吧多次到访可以有多条独立的经历。个人时间轴按具体饮用和经历回顾，如何呈现分组卡片仍待交互细化。

### 3. 场景专属信息（可选）

| 场景 | 共用基础记录 | 建议出现的可选专属字段 |
| --- | --- | --- |
| 酒吧饮用 | 酒名/酒款关联、时间、照片、感受等 | 酒吧、酒单原名、价格、探店经历关联 |
| 在家自调 | 同上 | 配方版本、配料用量、制作心得 |
| 其他场景 | 同上 | 自定义地点、备注 |

这里的专属字段为**设计建议**，用户确认的是「基础字段统一、专属字段按场景出现且可跳过」，并非逐一确定全部字段名、校验规则。

### 4. 个人页面与回顾

- 从底部「我的」进入个人饮酒日记；日记作为相对独立的个人功能页，主视图按时间排列。
- 同一组记录可从不同视角回顾：饮酒时间轴、同款酒归集、按酒吧归集；日历、照片墙和多维筛选逐步补足，不需要存储成多个相互矛盾的对象。
- 「我的」首页采用功能入口还是直接展示时间轴，以及「酒吧足迹」「我的酒款」入口的视觉布局，是此前讨论中的**建议，尚未被用户最终选择**。
- 对外公开个人主页不可展示未主动发布的日记、地点轨迹或私人配方。

## 四、记录、分享、评价、知识库必须分开

- **个人饮用记录**：默认私人、可编辑、可补充、可独立存在。
- **探店／饮酒经历**：用于把某次体验里的多杯酒关联起来，默认私人。
- **社区公开内容**：通过用户独立、主动的分享操作产生；不得仅因保存或修改个人记录而自动公开。
- **酒吧公开评价**：属于另一条明确的评价与审核流程。已有 PD-017～021 关于有效总分、匿名和一人同店最新有效评分的规则仍适用于**正式公开评价**，不因此自动套用于私人的饮酒记录与个人打分。
- **公共鸡尾酒及配方知识库**：私人自由记录不自动升级为公共投稿；知识库条目/配方版本关联可后补，私人记录不等于公共配方的改编稿。

## 五、与旧版方案的冲突与处理状态

| 旧版条目 | 早期曾选方向 | 本轮处理 |
| --- | --- | --- |
| UI-003：打卡动态可见性 | 完成打卡默认公开 | **待重新审议**；不适用于新确认的「个人饮酒记录默认私人」。正式公共打卡是否单独保留与如何发布，后续再定。 |
| UI-003：快速星级联动 | 打卡完成后，星级自动提交独立公开评价 | **待重新审议**；个人记录中的评分不能据此自动公开为酒吧评价。若设计单独的公开打卡/评价工作流，必须再明确。 |
| UI-002：全局「＋」五项创作入口 | 以打卡／评价／发帖等创作为主 | 入口及导航方向有历史讨论，但如何提供「快速记录一杯酒／一次经历」需要重排信息架构，**未做最终新选择**。 |
| PD-005/007/008/009 等 | 商家推广、榜单、社交等较完整功能 | **保留历史决策，不擅自宣称全部取消**；必要性与优先级要重新以个人价值为基准评估。 |

早期文档的决定并非数据错误，而是访谈过程的一部分；后续实现与验收应优先检查本轮已明确的默认私人记录原则，冲突事项必须产品复核后再实施。

## 六、建议的非实现级验收示例（尚未正式批准）

1. 未找到的原创特调可以存成私人饮用记录；后续再关联酒款，不产生公共配方投稿。
2. 同一款鸡尾酒喝三次产生三条独立饮用记录，但个人酒款档案可汇总这三次体验。
3. 同一次探店可以添加多杯；先记录后关联不产生新的重复饮用记录。
4. 同一天两次饮酒不因日期相同被系统擅自合并。
5. 私人记录补充文字、照片或个人评分不会自动产生帖子或对酒吧的公开星级。
6. 自己在「我的」里能回看全部个人记录；其他用户只能看到明确选择分享的内容。

## 七、仍待提问

- 「我的」首页功能入口与饮酒时间轴的层级，以及全局「＋」是否增加独立「记一杯酒」等快捷入口。
- 用户主动将私人记录分享到社区时，是分享快照还是长期同步、能否撤回公开、删除与权限如何独立处理。
- 个人酒款档案如何区分经典酒款、不同配方版本、原创酒款和别名；错误关联如何撤销。
- 个人评分的含义（对一杯出品的主观感受、对配方版本的评价、对酒吧的正式星级）与展现形式。
- 1.0 开发优先级（PD-027）、存储/同步/离线、多设备隐私、历史记录迁移细节。
