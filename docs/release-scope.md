# 酒迹 · 1.0 与后续版本范围控制（草案）

目标：把已经确认的长期功能方向和已明确约束的 1.0 交付边界分开。**这是 PRD 范围清单，不是已开发、已部署或测试通过清单。** 版本时间与全部其他模块的最终上线优先级仍待确认（PD-027）。

## 明确的 1.0 取舍

| 模块 | 1.0 的目标及约束 | 明确不在 1.0 的能力 |
| --- | --- | --- |
| 酒吧活动与预约（PD-024/025） | 酒吧基本活动列表/详情、真实的外部预约与报名入口；认证商家维护官方活动；用户可推荐或纠错，审核后注明来源 | 站内订座、实时空位、候补、支付票务 |
| 活动高级发现（PD-026） | 不作为 1.0 交付项；活动展示仍遵循上一行 | **活动日历、活动收藏、开始提醒、关注酒吧、活动动态和自愿订阅通知，以及进阶活动筛选** |
| 酒单与酒款（PD-023） | 已确认先 C：结构化菜单与酒款知识库双向关联；应进入首版需求评估与验收拆分，但用户未单独指明必须在 1.0 同期全部交付 | D 阶段原创特调档案、调酒师署名、季节酒单、菜单历史、授权专属配方等 |
| 调酒（PD-010/011/012） | 已确认先做 C：酒款、独立配方版本、评分、投稿/改编与协作；材料和杯型规则辅助模块优先级再定 | D 阶段 AI 智能推荐、长期偏好学习和智能创作 |
| 酒吧评价（PD-017～022） | 已确认透明的评分治理、评价与社区可选关联、匿名身份、认证商家回复等**产品原则**；各功能是否都是 1.0 发布阻塞项仍待确认 | 不把复杂、不透明的加权五星公式写成首版目标 |
| 社区（PD-009/020） | 已确认图文社交方向和评价/帖子的关联机制；具体首发最小上线集合待定 | 尚未确认短视频、私信、直播、群聊 |
| 账号、审核、数据可信（PD-003/004/006） | 游客公开只读、真实用户登录与个人操作权限、AI 初审+人工复核原则已确定；这些属于上线前需要评估的基础依赖 | 不将开发测试管理员令牌作为正式登录 |

**解释：** PD-002 的「第一版尽可能完整」是产品方向，不能据此把尚未确定的功能全部标为 1.0 必做。尤其「PD-026 1.0 不上」是用户明确指定的排期约束，开发排期不得自动将它升格为首版验收条件。

## 版本路线建议（未最终确认）

- **1.0（基础业务连通）**：酒吧发现、已确认的账号与内容治理基础、酒吧基本信息与活动展示/外部入口；其他图文、评分、酒单、配方能力按下一轮优先级访谈排出必要与可延后项。
- **1.x 或 2.0（进阶体验）**：PD-026 全部活动发现与提醒；PD-023 D 的商家专属酒单作品能力；PD-010 D 的 AI 配方推荐与个性化增强。具体阶段顺序待定。
- **多平台**：先微信小程序，再根据迁移、后台与客户端验证推进 iOS/Android/HarmonyOS NEXT。不能把仅有适配脚手架说成已发布。

## 状态与依赖

现阶段仓库只有原型、测试数据、部分客户端和测试同步协议：例如旧 `recipes` 使用扁平字段，尚无独立配方版本模型、生产级用户认证或完整动态活动后台。不能直接把本文需求写成「已经实现」。开发需完成：

1. 权限与认证：用户注册、微信快捷登录/手机号登录、商家认证与权限隔离、匿名评价公开投影。
2. 结构化数据与迁移：酒款/配方版本、评分聚合、探店/评价/帖子、菜单、活动、审核、标签投票与证据。
3. 审核、申诉、反作弊：合理差评保护、商家回复和普通用户内容审核、证据访问权限。
4. API 与多端：优先搭建稳定接口、分页与审计，再分端接入，覆盖匿名浏览、账号写入、离线同步及版本冲突。
5. 端到端验收：真实商家资料有效性、评分样本和到访可信度、外部链接可访问性、匿名安全、活动过期归档、1.0 延期功能不误开放。

## 明确留待 PD-027 讨论

哪些能力是 1.0「上线前必须完成」，哪些是「首发候选、非阻塞」，哪些进入后续阶段？需按地图发现、评分评论、图文社区、调酒配方、结构化酒单、商家后台、内容治理逐模块建立有优先级和资源预算的验收清单。
