# 酒迹 · 酒吧评价、探店、回复与评分设计草案

适用决策：PD-003/004/008/009/015～022。此文档以已确认的产品原则为约束；具体数据库、接口与算法为待实施设计，不应误认为已开发。

## 一、评价、社区和一次探店的业务边界

- **一次探店体验 visit**：一位已登录用户关联某家酒吧的一次体验记录，可选择填写到访日期、内容或自愿证据；不要求先上传到访证据才能评分。
- **酒吧评价 review**：针对具体酒吧的总体星级以及可选分项（酒水品质、调酒技术、服务、环境、性价比）、文字感受、展示身份设置。评价用于酒吧详情与评分计算。
- **探店帖子 post**：用于图文、话题和社交互动；可以独立创建或关联到一条探店体验 / 评价，不能因展示一次内容而重复计分。
- 用户可只发评价、只发社区帖子，或在一次填写中**明确选择**同时发布两者。两者的状态和删除动作保持独立；评论互动不自动等同于新增评价。
- 对匿名评价，公开署名探店帖的关联可能造成去匿名，前端必须提醒并避免未经确认的公开双向链接。

## 二、评分口径（PD-017/018/019）

- 用户自主选择总体 1～5 星。分项评分不参与总星级计算；没体验的分项可跳过，不视为零。
- 对每家酒吧，查找每个有效用户的**最新一条审核有效的总体星级**，将这些星级做普通算术平均。用户每次复访的有效图文记录都保留，旧评分不再重复计入总体平均。
- 最新一次评论在待审核或判为无效时，统计应退回到该用户上一条仍有效的总体评分；不能计入待审数据，也不得把同一用户的多条有效历史星级并行计入。
- 平均分与有效评分人数同时显示；保留充分小数用于计算，展示时可四舍五入，精度和阈值仍待确认。低样本时以警示或不足信息说明，不伪造分数。
- 到访标识、用户等级、评价字数、评论时间等**不直接改变有效总体星级的个人权重**；时间和有效样本量可以作为另一个「自然榜单／推荐」模型的因素，但不改变公开均分。
- 举报、审核、复核、撤销、编辑和软删除后需要重算。不得因商家付费而改变评分资格或星级。

**示例：**某酒吧 A 用户先给 3 星、后给 5 星；B 用户给 4 星。公开均分是 `(5+4)/2=4.5`，有效评分人数为 2，不是 `(3+5+4)/3=4.0`。

## 三、多维度评价与内容审核

- 评分状态提议使用 `draft / pending / published / hidden / removed / appealed`，是否允许 AI 直接通过低风险文本需遵循 PD-004 的审核政策，而非简单认为模型百分百可靠。
- 审核重心是虚假商家关联、自评刷评、营销诱导、机器人群控、针对性骚扰与不实指控；正常主观差评不应因商家投诉而自动删除。
- 分项平均分应单独统计有效评分人数；不同人只填写了部分维度时，每个维度样本量会不同，缺项不能按 0 分。
- 商家与编辑榜单不能购买统计修正资格；外部评分如依法引入，单独标识来源及时间，不得合并到酒迹用户评分。

## 四、公开／匿名展示与隐私（PD-021）

- 评价作者必须是已认证的酒迹内部账号。展示选择 `public_profile` 或 `anonymous`，影响对外昵称、头像和个人主页链接，不改变后台审核权。
- 匿名评价不能在公开响应中泄露用户 ID、真实昵称、头像 URL、个人主页引用、关联用户帖、签到位置轨迹、消费凭证等可识别字段；商家后台权限亦不能越权读取。
- 用户主动关联自己的公开署名探店帖时，明确提醒两者关联可识别身份；可取消关联或选择不公开关联。实际默认公开范围和历史转换体验后续交互验收。
- 因多端分享、搜索索引、消息通知、缓存而生成的引用也应执行同样的匿名投影规则。公开评价与作者后台访问必须是两类独立 API 数据视图。
- 对内容举报和申诉保留必要审计信息，访问受严格权限控制；具体保留期限按合法性和隐私设计单独确认。

## 五、商家官方回复（PD-022）

- 仅通过 PD-005 店铺认证且拥有该店经营权限的账号可针对自己店的评价发表带「商家官方回复」标识的内容；评价者可以继续补充回应。
- 商家不可编辑评价、查看匿名者账号信息、撤销分数或强制删差评。用户补充回应也不能以回复次数多而多次计分。
- 官方回复与补充回应须纳入内容审核、举报、反骚扰限流及人工复核；争议可申诉，回复修改留痕。默认次数、冷却期、编辑限制尚未确认。
- 商家变更经营主体、撤销认证、评价隐藏时的回复显示规则需在权限测试中明确。

## 六、数据模型和接口草案（未实施）

```text
bar_visits(
  id, bar_id, user_id, visited_on_nullable, created_at
)
bar_reviews(
  id, visit_id_nullable, bar_id, author_user_id,
  overall_stars_nullable, dimensions_json_nullable, body_nullable,
  identity_visibility, moderation_status, created_at, updated_at

review_audit_events(
  id, review_id, actor_kind, actor_id, action, previous_state, next_state, created_at
)
visit_evidence(
  id, visit_id, user_id, kind, private_blob_ref, verification_status,
  submitted_at, verified_at_nullable, expires_at_nullable
)
posts(
  id, author_user_id, linked_visit_id_nullable,
  linked_review_id_nullable, visibility, moderation_status, ...
)
review_replies(
  id, review_id, user_id, role, reply_to_id_nullable,
  body, moderation_status, created_at, updated_at
)
```

- 访客只获取公开审定内容。普通用户需要登录才能发评价、投稿或回复；商家回复额外验证店铺角色。
- 评分聚合与评论记录分开实现；**按 bar_id 与 author_user_id 选择最新有效总体评分**，在业务读取层和统计层避免重复计数。
- 可选按星级明细构建失效可重算的聚合缓存，不能将缓存误认为真相来源。
- 评价与探店帖一键发布涉及两个内容对象，需事务/幂等设计，避免部分失败后重复生成帖子或重复评价。
- 对实名用户数据、匿名公开投影、商家操作身份做权限隔离。旧 `posts` 和 `bars` 数据不能因迁移而错误造出公开评分。

**建议接口方向（尚未部署）：**`GET /v2/bars/:id/reviews`、`POST /v2/bars/:id/visits`、`POST /v2/bars/:id/reviews`、`GET /v2/bars/:id/rating-summary`、`POST /v2/reviews/:id/replies`、`POST /v2/visits/:id/evidence`。版本与 URL 只是方案示例，不表示已完成后端。

## 七、验收样例

1. 同用户对同店先 3 星后 5 星，另用户 4 星，总分 4.5，人数 2；旧探店笔记仍能查看。
2. 新评分被判为待审时，不替换之前已发布的有效评分；恢复审核通过后才更新总分。
3. 分项星级与总体星级独立，缺项不计 0。
4. 只发帖不产生新酒吧评分；一个评价可关联一篇探店帖但不会产生两个分数。
5. 匿名评价在访客、商家、搜索分享等公共响应中均不返回作者身份；关联署名帖子前明确提示隐私风险。
6. 商家只能回复有权限的店铺评价，不能改评价和查匿名作者；双方被举报内容能够审核及申诉。
7. 经合法来源引用的外部评分不参与酒迹总体算术平均；自然榜单与广告隔离。
