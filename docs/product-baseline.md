## 1. 产品定位和使用场景

酒迹聚焦四件事：**找到合适的酒吧、查询并尝试鸡尾酒、记录每次饮用和探店经历、与同好自主分享**。个人工具价值独立成立，社区与商家功能不能反向迫使个人用户公开内容、积累打卡、给商家打分或维持社交活跃。

| 场景 | 用户真实目标 | 主要位置 |
| --- | --- | --- |
| 出去喝酒 | 地图找店、搜索与筛选、查看准确酒吧资料和酒单 | 地图 |
| 自己调酒 | 按酒款与配方版本查询、看材料和步骤、记制作经历 | 调酒 |
| 记住一杯酒 | 几秒内先保存，可稍后补充照片、感受、地点或配方 | 中央「＋」/我的 |
| 记录探店 | 一次探店关联多杯酒，或先记单杯后关联 | 中央「＋」/地图/我的 |
| 回顾体验 | 时间轴、按酒款和酒吧归集；后期日历和照片墙 | 我的 |
| 自愿分享 | 把选定内容发表到社区并参与讨论 | 社区/记录详情 |
| 纠正数据 | 投稿酒吧信息/酒单/活动线索并接受审核 | 酒吧详情/商家端 |

**非目标（近期建议）**：以广告作为信息架构核心；自动发布私密记录；强制评分；通过连续饮酒激励提升消费频率；站内订座、支付、酒类交易；短视频、直播、私信或内容流量排名作为首发依赖。

## 2. 已确认的八项个人记录决策（JR）

1. **JR-001**：个人记录优先；社区分享由用户主动选择，默认私人。
2. **JR-002**：每杯酒与每次探店都可独立记录、互相关联；家中调酒无需绑定酒吧。
3. **JR-003**：快速保存、随时补充，不强制完整表单。
4. **JR-004**：时间轴作为个人记录主视图；日历、照片墙和多维筛选逐步增加。
5. **JR-005**：同款酒每次饮用独立留存，同时按酒款归集到个人档案。
6. **JR-006**：输入酒名推荐知识库酒款/具体配方版本；不匹配时能自由创建私人记录，之后可关联，绝不自动向公共知识库投稿。
7. **JR-007**：基础表单统一，酒吧饮用、在家自调等场景提供可跳过的扩展字段。
8. **JR-008**：探店可先建立再添加多杯，也可先逐杯记录后手动归集，不根据日期或位置擅自合并。

私密记录中的个人评分、正式酒吧评价和针对具体配方版本的公开评分**分别建模**。用户给私人饮用记录打 4 星，不代表对酒吧或配方发表了公开评分。

## 3. 最新 UI 决策（UI-004）

**已确认**：全局采用 **A「城市极简」**的页面与交互风格，参考 Google 地图的轻量工具式体验；**品牌主色沿用旧主题棕红色 `#82442F`**，不要采用 A 主题以前的暗玫红色 `#903F59`。

- 视觉基础：浅灰白背景 `#F7F5F5`、白色内容表面 `#FFFFFF`、正文 `#242329`、弱分隔线 `#E6E6E8`、棕红品牌色 `#82442F`。这些是**新目标 Token**，尚未写入旧代码。
- 地图页优先；搜索栏悬浮在地图上，横向筛选胶囊，地点标记点击后显示可展开的底部信息面板；酒吧详情强调真实照片、可核实资料、酒单和明确操作。
- 避免装饰性英文大标题、满屏渐变、过量圆角/卡片/阴影和复杂数据仪表板。轻量系统字体和分隔线优先。
- 社区手机双列瀑布流、宽屏三至四列的已确认布局原则保留，但卡片视觉按 A 简化。
- 现有原生微信的主题注册表和设计包仍以 `editorial` 为默认，且旧 `minimal` 强调色为 `#903F59`；改为目标主题需要统一调整各平台 Token、导航样式、相关快照/主题测试和迁移行为，**目前还没改代码**。
- 地图首次打开时底部面板的默认高度有「少量预览 / 半屏 / 选中才出现」三个设计候选；**尚未收到用户对该子项的选定**。建议先用少量预览做可变原型，待可用性测试或正式确认后冻结。
- 完整组件、交互状态与设计 Token 见 [A 城市极简 UI 规范](ui-a-minimal-spec.md)。

## 4. 信息架构（顶层已讨论；中央动作内容尚待最终冻结）

```text
地图               调酒             ＋             社区             我的
真实点位/筛选       酒款/配方         全局动作         图文内容         私人首页
地图列表            配方版本         快速记一杯酒*     双列瀑布流       饮酒日记
酒吧详情            配方工具         记一次探店*      帖子详情         酒吧足迹
酒单/活动           自制作品         分享内容*        评论互动         我的酒款
想去/导航           记录制作         推荐新酒吧*      收藏/关注*       收藏/草稿/设置
```

`*` 为建议的新入口/延续能力，并非菜单条目都已逐项确认。

已确认底部四个 Tab 的意图为 **地图｜调酒｜社区｜我的**，中间「＋」是一个**全局动作按钮而非第五个 Tab**。旧版「＋」主要是五项发布动作；结合新个人记录原则，**建议**新菜单优先「记一杯酒」「记一次探店」「发布内容」，将酒吧评价/推荐新酒吧设为上下文入口或次级动作。是否继续保留旧菜单的全部五个独立按钮，**待裁定**，避免在小屏挤出过多选项。

「我的」是私人数据的入口，**不等于其他用户可看的公开个人主页**。建议首页用「饮酒日记、酒吧足迹、我的酒款、收藏」四个轻量入口，日记进入后以时间轴显示；该首页是否直接呈现时间轴还未最终被用户裁定。

## 5. 业务对象与可见性

| 对象 | 用户实际含义 | 默认 | 与其他对象的关系 |
| --- | --- | --- | --- |
| 单次饮用 `drink_entry` | 这一次喝/调了一杯什么 | 私人 | 可关联酒款、配方版本、探店 |
| 一次经历 `visit_session` | 某次探店/饮用场景 | 私人 | 关联 0～N 杯饮用 |
| 个人酒款档案 | 同款饮用的归集视图 | 私人 | 根据用户确认的酒款关联计算，不丢单次记录 |
| 酒款 `cocktail` | 可共享的酒款概念 | 公共经审核 | 关联多个版本 |
| 配方版本 `recipe_variant` | 具体作者、用量、技法 | 可私密或公共 | 可作为个人记录的引用 |
| 社区帖子 `post` | 用户明确发表的内容 | 由发布操作决定 | 可引用饮用或探店的**公开快照** |
| 酒吧正式评价 `bar_review` | 用户自愿提交的酒吧评价 | 有独立审核/身份选项 | 计分仅按 PD-017～021 |
| 酒吧数据/酒单/活动 | 来源可核实的地点资料 | 审核后公开 | 非官方投稿不得冒充商家 |

**强约束**：保存、编辑私人饮用记录、关联探店、打个人分，均不得触发公开帖子、公开酒吧评分、自动知识库投稿或精确地点披露。可见性由服务端独立校验，不依赖前端隐藏按钮。

旧版 UI-003「打卡默认公开」「填星自动提交正式评价」是历史曾选 B 的方案，已与新的私人记录定位发生冲突：**在重新裁定前不得实现为个人记录默认动作**。历史选择仍留在 [决策文档](product-decisions.md) 以供追溯。

## 6. 首版范围：确认项、建议排期与保留边界

用户已决定先做微信小程序、广州作为数据试点，跨平台逐步推进；PD-026 的高级活动日历/收藏/提醒/关注/订阅**明确不进入 1.0**，但 PD-024/025 的基础活动展示及真实外部入口仍保留。

下面仅是**建议的可实施排序**，不把早期「尽可能完整」误解释为所有功能同天上线，也不能将建议性排期冒充最终批准：

| 阶段 | 开发目标 | 最重要的结果 |
| --- | --- | --- |
| W0 工程清理与 UI 基础 | A 视觉 Token、路由/导航、真实地图与数据质量基线 | 小程序正常编译，风格统一，不回归旧页面 |
| W1 私人记录纵向切片 | 记一杯、记一次探店、保存/编辑、互相关联、时间轴 | 无需社交、无需商家数据也能形成完整个人价值 |
| W2 酒款和地图闭环 | 酒款/配方版本、广州酒吧搜索筛选/详情/真实坐标/导航 | 可以从酒款或地图创建私人记录 |
| W3 账号同步与安全 | 正式微信/手机号认证、私密数据隔离、迁移、离线冲突 | 可在设备间安全回顾；游客仅公开只读 |
| W4 社区与公开治理 | 自主发帖、照片、评论/点赞/举报、审核及必要评价边界 | 私人记录与社区安全分离 |
| W5 基础酒单/活动与测试 | 可信菜单、基本活动和外部预约入口、核验/错误回退 | 满足现有基本资料方向，不伪装为站内交易 |
| W6 发布验收 | 真机、弱网、无权限、账号注销、隐私/版权/备案与后台运维 | 能供真实用户稳定测试，而非只能演示 |

其中 W0～W2 可作为内部 Alpha 的最小纵向体验；W3～W6 涉及正式公开测试的阻塞依赖。商家认证与正式评价全套治理的具体 1.0 阻塞深度，需要 PD-027 再细分；**不能用此排期自动删去旧 PD-023～025 已确认的长期目标**。

## 8. 可以交给研发的要求

- 以 [微信开发路线](wechat-dev-roadmap.md) 的独立 Issue、依赖、验收门槛开展开发。
- 变更视觉时务必同时检查 `packages/design/tokens.json`、`miniprogram/utils/theme.js`（旧端）、`apps/wechat/src/app.config.ts` 与实际 Taro 页面样式/图标。**新主题必须统一棕红强调色**，不能只换一个文件。
- 生产与测试环境区分：原有 Sites 开发 API/设备短期令牌**不得**替代微信正式登录，不得把管理令牌写入前端。
- 未确认的 UI 行为以可配置原型处理，不让危险默认值入库；当上线依赖相应选择时再向产品负责人决策。
- 按用户上传与图片/UGC 的隐私及合法授权处理素材；地图要使用合法地图 SDK，不复制 Google 专有数据或商标视觉资源。
- 本批提交仅是**需求与开发准备**，没有改动页面代码或通过真机验收。

## 9. 待确认（不阻止工程脚手架，但阻止相关功能上线）

6. PD-027：完整商家认证、公开评价/回复、结构化酒单/活动的 1.0 阻塞等级和所需人力。
