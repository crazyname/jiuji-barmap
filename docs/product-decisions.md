### PD-001 · 城市范围

- 首发城市为**广州**，利用现有广州酒吧数据开展测试。
- 产品架构、地点数据模型及城市选择机制按**未来支持多城市**设计，逐步增加国内其他城市。
- 不把“全国首发”或“全球覆盖”作为第一版承诺；新增城市与数据规模另行排期。
- 对未经核实的酒吧位置，保持 `location: null`，不生成虚构坐标。

### PD-002 · 首个公开测试版

- 产品目标是尽量提供**完整、连贯的用户体验**，不是只发布单页或纯演示。
- 具体要包含哪些功能、哪些必须上线、哪些可以作为后续版本，须继续与产品决策者确认后写入 PRD 和验收清单。
- 本选择不意味着四个平台已经完成、所有功能已有线上后端，亦不等于尚未定义的功能自动列入开发承诺。
- 既定实施节奏：先完成微信小程序，提炼共享逻辑，再分阶段同步 iOS、Android 与 HarmonyOS NEXT。

### PD-003 · 登录及游客使用权限

- **游客**：无需登录即可浏览已公开的酒吧地图与酒吧资料、调酒配方、社区内容。
- **需要登录**：收藏与取消收藏、保存个人草稿或配方、发布探店帖子、点赞评论及其他与个人账号关联的操作。
- **跨端同步**：个人数据必须在可信的用户身份下保存和读取；不同用户的数据相互隔离，不使用公开共享令牌作为正式账号。
- **当前实现与目标不一致**：微信和 React Native 的早期客户端曾允许游客将收藏、草稿写到本机。后续开发需在个人操作入口增加登录门槛，并规划已有本机数据的安全迁移；不得因为现有功能可用就将“游客可以使用个人功能”写成产品要求。
- 正式登录选择已经在 PD-006 确认；游客历史数据处理方式仍**待后续确认**。

### PD-004 · 开放协作、商家认证与分级审核（B+C+D）

**用户投稿（B）**
- 已登录用户可推荐新酒吧、上传照片、补充资料和提出纠错申请。每次投稿保留申请人、目标酒吧、提交字段、依据、时间和审核状态。
- 投稿先经 AI 初审；对合规性和证据可明确判断、风险低的内容可以按制定的规则自动通过或标记为“待核实”。无法核实的位置、经营状态、来源不清的评分等不能仅凭 AI 推断为真实。
- 被拦截、存在争议或高影响的变更转人工审核，用户可以申请人工复核。

**认证酒吧经营账号（C）**
- 酒吧经营者可申请官方认证，经营主体、店铺控制权与真实性需要验证，AI 可辅助核查，但不能代替必要的人为确认。
- 认证账号可以维护该酒吧的官方资料、营业时间、活动、菜单、图片等。变更经过风险分级审核，关键资料需额外核验。
- 经营账号也是商业化入口；已确认商家免费认证和管理，仅广告推广与商业合作收费（见 PD-005），具体投放形式与价格待定。
- 商业付费不能获得免审特权、操作独立评价、隐匿真实差评或冒用用户投稿；推广内容必须明确标为广告/商业合作。

**社区协作申请（D）**
- 已登录用户可以对现有酒吧提交字段级修改申请与证据，例如地址、地铁出口、营业状态、价格、照片等。
- 原始官方记录在申请审核完成前不被普通用户直接覆盖。冲突与重复申请需要合并或提示人工裁决；保留版本历史及回滚能力。
- AI 初审负责去重、风险识别、格式合规检查和辅助查验；真实地点与经营资料需可靠证据支持。

**统一的内容治理原则**
1. 采用 **AI 辅助初审 → 风险分流 → 合规发布/待核实/人工审核**。高风险、证据冲突、投诉举报、商家主体认证、关键事实变更和 AI 低置信度判断交由人工处理。
2. AI 不直接作为不可申诉的最终裁决；用户可对处罚或驳回申请人工复核，管理员有权推翻 AI 结论。
3. 审核覆盖酒吧资料、帖子、评论、图片、商业推广与商家活动；不同类别有独立规范和阈值。
4. 重点治理虚假评价、刷屏、骚扰、恶意引流、暗广告、冒用商家、虚假地点与其他损害社区环境的行为。审核应兼顾合理的批评、客观差评与正常体验分享。
5. 审核留存可追溯记录：提交版本、审核主体（AI/人工）、判定依据、结果、申诉、回退和操作日志。对用户尽可能解释可操作的驳回原因。
6. AI 审核服务异常或缺乏足够证据时，不得自动批准高风险内容；进入待审队列并可升级人工。

**仍待确定**：自动通过的具体条件、内容审核时限、认证材料及法律合规细则。以上原则不表示相应后台与模型服务当前已完成开发。

### PD-005 · 商家免费经营管理、广告推广收费（A）

- 认证店铺由经营主体免费申请和管理；认证流程必须核验真实性，不以付费作为认证条件。
- 商家可免费维护官方资料，包括营业时间、地址、照片、酒单及一般店铺信息；为运营提供的数据分析和活动管理工具可逐步完善，不因使用管理功能而强制支付订阅费。
- 收入来源以清晰标识的广告、商业推广位、品牌活动合作为主。具体广告类型、计费方式、报价及投放审核细则留待后续决策。
- 商家不购买广告也享有正常收录、资料管理和审核权利。商业付费不得免审、篡改排名中的客观评价、隐藏真实差评或购买虚假好评。
- 与 B 的区别：B 可以对经营分析、高级活动管理工具等单独收费，A 优先保持商家经营管理免费，只对推广和广告变现。
- 不代表现在已经有支付或投放后台；商业化属于待开发业务模块。

### PD-006 · 微信优先、手机号注册和第三方身份绑定

- 选择 **A 为主，同时融合 C 的账号绑定与合并能力**。符合一般消费者应用的注册、登录、找回、退出与账号管理体验，不要求用户手动配置 API 或输入测试令牌。
- 微信小程序提供微信快捷登录；由客户端获取微信临时登录凭证、服务端校验微信身份后，创建或定位酒迹用户账户。
- **手机号注册登录不可缺少**：没有微信的用户也能通过手机号完成注册、验证与登录；手机号归属需要经过可靠验证。
- 微信侧可提供单独的“授权手机号”操作：经用户明确同意、平台授权及服务端校验成功后，可使用微信提供的已验证手机号码完成绑定，通常无需再重复短信验证码。**微信登录不等于自动获取手机号**；拒绝授权、权限不可用或号码需进一步核验时保留手动手机号验证入口。
- 支持账号中心绑定/解绑微信、手机号及后续确定的第三方认证渠道；同一位用户在微信、iOS、Android 与 HarmonyOS NEXT 登录后，使用**同一酒迹账户**同步收藏、草稿、配方、帖子等个人数据。
- 第三方账户合并必须由用户主动发起并验证待合并账号的控制权；不能仅凭昵称、手机号码文本或相似资料悄悄合并。被封禁或存在争议的账号不能借合并绕过审核。
- 所有第三方身份与登录方式映射到酒迹自己的唯一用户 ID。通过服务器颁发的用户会话访问数据；第三方平台的密钥、微信 session_key、后台管理员令牌不会下发给客户端。
- 手机号变更、账号注销、身份解绑、设备退出、异常登录核验及个人资料迁移需要纳入后续验收；具体可支持的第三方平台和找回规则另行确认。
- 当前 Sites 设备令牌只用于研发联调，**不是正式消费者登录**；真实登录与账号合并服务仍待实现。

参考详细设计：[账号与身份系统](auth-design.md)。

### PD-007 · 完整酒吧探索平台（C）

产品目标：酒迹不仅用于在地图上找到酒吧，还应帮助用户比较、探索与规划酒吧体验。

**首个公开测试版目标功能范围**
- 地图与列表两种浏览模式，支持相互切换；地图点位与列表数据来自同一套酒吧记录。
- 酒吧名称、关键词、地区/商圈等搜索，结合距离、价格、酒吧类型、营业状态等条件筛选；具体筛选字段的定义与组合规则在交互规范中细化。
- 可浏览酒吧详情、查看已核实的地址/位置、进入导航及收藏清单；按 PD-003，个人收藏等操作须登录。
- 特色榜单（例如主题特色、编辑精选等）及酒吧主题合集，展示相应内容来源和收录依据。
- 个性化推荐能力，以已获授权的数据与可解释的偏好作为依据；没有登录或足够偏好数据时提供非个性化探索内容，不凭空宣称用户喜好。
- 酒吧探索路线：支持将多个酒吧编排成可浏览的路线，连接地图、酒吧详情与必要的导航操作；路线的生成方式、路线数量限制和地图服务适配留待细化。

**数据真实性、商业化和交互约束**
- 坐标未核实的酒吧依然保留 `location: null`，不能擅自投放精确地图标记或生成伪造路线。
- 排名与推荐不能因为商家付费而伪装成自然排序；商业推广需要明显标识，并遵守 PD-004 和 PD-005。
- 评价体系的组成已在 PD-008 确定；具体权重、榜单算法、可信度和反刷评机制仍须独立设计并验收。
- 全国扩展按 PD-001 逐城市推进，城市筛选与数据模型需支持后续扩展。
- 这是**产品要求而非完成状态**：当前客户端已有部分地图浏览、搜索和地点详情脚手架；榜单、个性化推荐与探索路线等进阶能力尚须开发并单独验收。

### PD-008 · 综合评分与真实体验评价体系（D）

- **多维度用户评分**：已登录用户可围绕酒水品质、调酒表现、服务、环境、性价比等维度评价酒吧；正式评价维度、各维度权重、分制、最低有效样本量，以及是否允许未去店的评价，留待后续规则确认。
- **真实探店评价**：支持文字、照片、到访感受等与酒吧关联的评价；应明确区分个人体验、商业合作及未经核实的陈述。真实差评不得因商家购买广告或投诉而被无故移除。
- **特色标签**：建立可搜索、可展示的酒吧特色标签；标签可来自编辑资料与用户建议，但须有来源与适当审核，避免标签刷量干扰推荐。
- **编辑榜单与主题精选**：可以按主题制作编辑榜单和合集，展示策划主体、更新时间和选入依据；编辑精选不等同于用户评分排名，也不能把赞助广告伪装成编辑推荐。
- **合法的外部评分参考**：在取得适当授权、遵守外部平台协议和适用规则的前提下引用评分信息，明确标注平台来源、抓取/更新时间、评分尺度及可能的样本差异。不得无授权抓取或擅自把外部分数混入「酒迹用户评分」，不可引用时就不展示该来源。
- **反作弊与风控**：对虚假评价、诱导评价、批量刷分、商家自评和异常互动实施 AI 辅助风险识别与人工审核；用户可申诉，正常的真实负面体验应得到保护。具体频次限制、证据与处罚阈值另行定义。
- **商业中立性**：自然评分、编辑榜单、付费推广分栏或清晰标记，广告费用不得直接改变独立评分结果。
- **技术与发布状态**：这是产品目标，不意味着当前已有评价、评分聚合、榜单计算、外部平台评分授权或反作弊模型的完整实现。

**后续待确认**：多维度评分权重、排序算法、评价频率、已到访证明机制、外部平台授权路径、编辑榜单评选流程及样本量不足时的显示方式。

### PD-009 · 完整图文社交社区（B）

**内容与发现**
- 用户可浏览公开图文探店、品酒体验及与酒吧相关的社区内容；发帖、修改、删除本人内容等个人操作需要登录，遵守 PD-003。
- 已登录用户可上传图文、关联准确的酒吧条目、添加话题标签；发布内容应包含清晰的作者身份及发布时间。
- 社区可呈现公开内容推荐/热门内容、关注动态和话题聚合；其排序依据与反刷量标准留待设计。

**社交互动**
- 支持对帖子点赞、收藏、发表评论、回复评论，允许作者及其他用户在规范内交流；评论层级、编辑时限及删除规则待确定。
- 支持关注和取消关注其他用户、查看公开个人主页、发布记录及关注动态；隐私可见性、拉黑、限制骚扰及被关注用户保护机制需要具体设计。
- 支持内容分享（平台允许的分享渠道），并提供举报入口；内容创建和社交操作必须先登录。

**审核与社区质量**
- 统一接入 PD-004 的 AI 辅助审核、风险分流、人工复核、申诉和审核记录，范围包括帖子、图片、评论、用户名/简介及话题内容。
- 重点识别刷屏、网络骚扰、造谣、伪装用户的商业宣传、刷赞刷粉及不实探店；允许用户陈述真实的主观体验和合理批评。
- 商家/品牌合作、付费推广的发布者身份及广告性质必须明确标注；不得购买虚假互动或以商业合作干预正常评价及榜单。
- 为防范滥用，需要具备举报处理、用户屏蔽/拉黑、限流/限制互动、后台操作日志及违规申诉等管理能力；处罚规则待具体制定。

**本次未决定的内容**
- 本次选择的是完整**图文**社交社区，不自动包含短视频上传、独立视频信息流、私信、直播或用户群聊；这些功能如需首版实现，须再次确认。
- 关注/推荐算法、内容排序权重、话题治理及反垃圾阈值、内容保留和可见性规则仍待补充。
- **这是产品目标，不是当前完成状态**：现有图文和同步功能是早期实现，关注关系、评论树、审核系统及账号权限仍需开发测试。

### PD-010 · 调酒知识库、多人版本与智能推荐（先 C，长期 D）

用户明确：**整体产品愿景为 D（智能调酒助手），但先把 C（调酒知识库 + 用户创作平台）做好**。因此不能将完整 AI 生成功能误写成首版已承诺交付，也不应将调酒版块简化为一张扁平配方表。

**酒款、版本与社区评价**
- 以**酒款（Cocktail/Drink）**作为入口；一款酒可关联多份不同来源、比例、做法或风格的**配方版本（Recipe Variant）**，并保留各版本作者和来源。
- 登录用户可以创建原创配方、保存私人版本、公开发布、分享成品照片、记录修改历史并关联社区帖子。
- 用户**只对具体配方版本独立评分**，同款酒的不同版本能单独比较；酒款主页根据这些版本评分展示有来源标识的汇总参考（详见 PD-011），聚合算法仍待定。
- 酒款有可管理的标签（例如风味、基酒、酒精度类别、技法、饮用场景等），支持浏览和筛选。标签提交与滥用治理受 PD-004 约束；精确定义稍后单独确认。
- **酒吧也应支持标签体系**；先记录跨模块需求，但用户明确希望日后再细谈酒吧标签，不在本次替用户决定其具体维度。

**配方发现和制作体验**
- 允许用户录入现有材料（包括是否有某种基酒、辅料、果汁等），筛选“可直接制作 / 缺少少量材料 / 无法制作”的候选配方；同义材料、可选装饰、替换规则应有明确定义。
- 可以选择杯型并调整杯子容积/目标出品量；软件据配方的份数、非线性因素和可调节部分给出计算结果，不得机械承诺所有配料都可以严格等比例替换。冰块占比、碳酸补足和分层等需要特别提示。
- 根据偏好的酸甜苦、烈度、酒体、口味标签等条件推荐适合的**酒款或配方版本**。初期可用标签与确定性匹配，不强依赖生成式 AI。
- 未来可以使用候选配方卡片进行“喜欢 / 不喜欢”反馈，用于改进个性化推荐。**用户原始交互设想是左滑喜欢、右滑不喜欢**；是否沿用此方向，需在正式交互设计中测试确认，并提供明显的喜欢/不喜欢按钮，不能仅依靠滑动手势。
- 长期 D 阶段加入 AI 辅助调酒：现有材料搭配、偏好学习、材料替代与原创配方建议；需避免编造配方来源，并明确区分用户内容、编辑内容及 AI 生成建议。

**初步交付划分（建议，尚未最终确认）**
- **C 核心**：可检索知识库、酒款与配方版本关系、配方详情、用户投稿/私密配方/发布、成品图、配方评分、酒款标签及相关技法教程。
- **C 能扩展的规则功能**：现有材料匹配、杯型/容量换算、根据口味标签排序候选酒款。这些不必等待 AI 模型上线，可尽早在 C 阶段建设；是否列为首版必备留待后续明确。
- **D 智能增强**：个性化滑卡反馈、持续学习、AI 推荐与创新配方/替换建议，待相应模型评估、成本控制及内容安全验收后上线。

**规则与数据约束**
- 标签应为可审核、可追溯的结构化关联，而不是随意拼接的字符串。酒款与酒吧共享标签管理思路但不得误认为同一标签直接适用所有实体。
- 配方材料按**结构化配料行**存储（材料、用量、单位、是否可选、用途）；否则难以准确筛选库存、计算目标容量和提供替代建议。
- **配方历史版本**（同一作者修订）与**同酒款不同配方变体**（不同作者/做法）分开建模，避免一次编辑变成全新酒款或覆盖他人作品。
- 用户评分与偏好滑动记录分别存储；配方评分不是匿名行为，防刷评须接入 PD-004 的风险审核。
- 推荐应解释依据，处理材料禁忌、酒精度、过敏信息、不可替代材料和未验证的 AI 建议；不保证所有组合都可饮用或成功。

进一步的实体草案、任务分期及未决问题见 [调酒模块设计](cocktails-design.md)。

### PD-011 · 配方独立评分、酒款汇总展示（C）

- **评分对象**：登录用户对某份具体的配方版本（`recipe_variant_id`）评分或评价，酒款本体（`cocktail_id`）不接受另一套独立的用户打分，以免用户误以为评价对象相同。
- **独立展示**：同一款酒下的不同作者、做法及配料比例分别拥有自己的有效评分与评价记录，不因某个版本受到欢迎而直接覆盖其他版本的数据。
- **酒款主页**：汇总展示所有已公开、有效的配方版本的评分分布、评价量、版本数量和代表性版本。酒款页面可显示“版本评分汇总参考”，但**必须标注该信息来自配方评分聚合，不是用户直接给酒款打出的分数**。
- **透明性**：对每个版本以及汇总值展示样本量、覆盖的版本数、有效评价范围和计算口径。没有足够样本、数据被审核撤销或算法不适用时展示“评分不足”，不制造看似精确的数值。
- **防止误导与刷分**：同一用户对同一配方的多次修改应按明确的去重与更新规则计算；重复、异常或违规评分按 PD-004 风控处理。付费推广不得影响有效评分或自然汇总。
- **数据模型**：`recipe_ratings` 以用户 ID 和配方版本 ID 关联；酒款级展示从这些已审核评价中计算或通过可失效缓存生成，不新增酒款直接评分来源。评分被删除、版本隐藏或审核状态变更时应重新计算。
- **未决定的细则**：采用简单均值、分层加权、贝叶斯校正或其他统计方案；最低样本阈值；一个用户能否评价同酒款多个版本；热度排序、按最新评分排序、版本对比展示方式，都留待后续开发文档细化。
- 此条为**产品决策**而非已经上线的服务能力，数据库、评价接口、风控与前端展示均需开发和测试。
