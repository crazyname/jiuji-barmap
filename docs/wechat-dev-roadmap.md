## 2. 开发操作与环境约束

- Node.js 20+；使用仓库规定的锁文件和安装流程。
- 仓库根目录：`npm ci`、`npm run check`、`npm run migration:status`。
- 微信 Taro：`cd apps/wechat && npm install && npm run dev:weapp`；或 `npm run build:weapp` 进行非 watch 编译。
- 微信开发者工具打开 `apps/wechat/dist/`，项目需配置合法 AppID、已授权域名与所需权限。**不要**提交真实 AppID 密钥、管理令牌、短信服务密钥等敏感信息。
- 开发测试 API 与正式后端地址必须通过环境配置注入；禁止在正式「我的」界面给普通用户暴露 URL 或测试令牌输入。
- 每个交付切片经过：TypeScript/合约检查、`npm run check`、微信生产构建、手动/自动化页面用例、至少一次真机兼容验收。缺少真机结果不可标记「微信已上线」。

## 3. 建议 Epic / Issue 切分

### W00 · 决策与分支准备

**任务**：确定新的产品基线导航、建立需要开发的 Issues、确认主分支保护/PR 规范/CI、记录当前 Taro 编译基线与可重现路径。旧默认公开打卡和快速打星自动发表**保持暂停**。选择开发 W1 时如仍有 UI 未决项，可先做可切换原型而不是依赖危险默认值。

**验收**：任一开发者可以克隆并运行已知基线；旧数据未丢；存在明确的回滚方式。*可作为第一个独立 PR。*

### W01 · A 视觉主题迁移（首选首个 UI PR）

**实现建议**：
1. 将目标主题定义为 `background=#F7F5F5, surface=#FFFFFF, accent=#82442F, foreground=#242329, border=#E6E6E8`。
2. 统一 `packages/design/tokens.json`、Taro `app.config.ts`、公共样式、地图/调酒/社区/我的的基础布局与四栏 Tab 选中态；原生微信主题设置如继续可用，需兼容迁移。
3. 不把同一语义主色错误套成旧 A 的 `#903F59`；选中项、操作按钮与地图选中标记均使用棕红。
4. 用真实占位规则替换渐变大海报、装饰性英文 kicker 和不必要的重卡片 UI。
5. 维护现有主题测试或新增视觉 Token/路由快照用例，不因更换默认值产生无意回归。

**验收**：四个 Tab 和页面弹层统一 A 风格，适配系统安全区和字体缩放；状态色可读；切换/返回不破坏原功能。*未完成不要发布截图称为正式新 UI。*

### W02 · 地图首页：搜索、标记、面板与列表

**实现建议**：真实地图为主体；上方悬浮搜索 + 标签；点击标记/列表项联动选中状态；底部面板 S0（地图浏览）、S1（酒吧预览）、S2（展开或进入详情）；可以手动切换地图和列表；保留筛选。关于地图首屏面板默认高度，先用可变原型和可用性测试，**不冒充用户已经选择了 A/B/C**。

**验收用例**：地图点位坐标必须有效；无坐标酒吧不伪造标记；地图滑动不误触面板；空结果/失败重试/无定位权限可用；列表同筛选；返回保留选中/筛选；真机验证 `map` 组件与 `cover-view`/弹层层级、导航路径。

### W03 · 私人记录底座：实体、权限和本机数据

**建议模型（仅草案）**：

```text
drink_entries(
  id, owner_user_id, drink_label, cocktail_id_nullable,
  recipe_variant_id_nullable, session_id_nullable,
  context_kind, consumed_at, note_nullable, private_rating_nullable,
  photo_refs_nullable, extra_fields_json,
  visibility=private, created_at, updated_at, client_mutation_id
)
visit_sessions(
  id, owner_user_id, bar_id_nullable, place_label_nullable,
  occurred_at_nullable, note_nullable,
  visibility=private, created_at, updated_at
)
```

不依赖公开帖子表承载私人日记。单次饮用可以为空探店关联；先存一杯后连到探店是一对多关系而不是复制对象；错误关联要可撤销。酒款知识库未匹配时 `cocktail_id` 保持空，而不是编造公共酒款。

**验收**：创建/编辑/删除/关联/取消关联/重启后恢复；不会自动发帖、公开评价或向知识库投稿；不同本机账号不串读；断网时可靠保存；重试不重复创建记录。

### W04 · 全局「＋」与快速记录一杯酒

**实现建议**：保留四个 Tab + 全局动作按钮；动作建议优先「记一杯酒」「记一次探店」，公共发布设独立明确入口。快速记录可先写酒名或选酒款后保存（最少必填字段待定），相应场景扩展字段可跳过。补充信息时保留原记录 ID。

**验收**：从任一 Tab 打开动作面板，取消还原页面；单杯记录一条不需创建探店；后补照片与感受不再次创建；未登录行为按 PD-003 引导，不能把数据放到别的用户账户；保存键使用「保存到我的日记」，公开行为显著分开。

### W05 · 探店经历/时间轴/个人酒款档案

**实现建议**：先建探店再连续添加多杯、先逐杯后关联探店两条路线；日记默认按日期回顾；同一款酒按用户确认的匹配归集。酒吧足迹是同批数据的另一视图，不是另一份副本。日历/照片墙增强排后。

**验收**：同一天同店两次探店不自动合并；不同地点同款酒产生多条记录；手动归集/解除不丢原记录；同一体验含三杯时记录数为三、不多发公共帖子；私密数据不出现在公开个人主页。

### W06 · 酒款知识库及调酒配方版本

**实现建议**：`cocktail` 与 `recipe_variant` 分层，酒名/别名搜索、明确版本作者/来源/用料与步骤；个人记录可选关联某款和某版本。原创酒在未录入知识库时可作为私人自由名称，后续主动匹配。

**验收**：同款多版本不会覆盖；知识库未匹配不阻止私人记录；私人配方与公开稿件权限隔离；来源可追溯；输入量/单位正确，不能仅凭显示名称混淆版本评分。

### W07 · 正式用户认证 + 私密同步 + 图片

**实现建议**：微信快捷登录 + 手机号路径及账户绑定原则沿用 PD-006。后端服务端鉴权、用户隔离、会话刷新、登出/撤销；本机队列幂等和版本冲突；对象存储经签名授权上传、隔离私有文件并去除不必要位置元数据。现有 Sites 测试环境只用于早期匿名读取/协议实验。

**验收**：A 登录不能读 B 的日记/照片；同账号两端新增记录可同步；断网补写后上线自动重试且不重复；冲突需明确提示；登录异常、注销和删除路径可测试；后台管理员/设备临时令牌绝不发给消费者。

### W08 · 社区发布与酒吧正式评价

**实现建议**：手机双列公开内容流，详情/评论、举报审核；从私人记录主动选择并预览要分享的信息，公众侧为独立资源。正式酒吧评价在独立流程明确提交，按 PD-017～021 做算术平均、每人同店最新有效一条、分项独立、匿名保护。旧 UI-003 自动发布两项规则暂停。

**验收**：私人记录不出现在公开列表；取消分享不误删私人日记；公开评价不因重复打卡多计分；匿名账户身份/地理位置不会通过 API、关联帖或商家接口泄露；违规举报/申诉闭环；普通真实差评不因商家赞助被任意删除。

### W09 · 酒单、基础活动、商家与可信数据

**实现建议**：先可读酒单（来源、更新时间、价格和供应状态不伪造），再做商家角色/审核流程；基础活动详情和外部真实报名/预订链接，时间过期退出「即将举办」。结构化酒单的公共酒款关联须可核实，不能擅自公开商家专属比例。

**验收**：普通用户不能冒用官方酒单/活动；链接无效不显示可预订；没有正式支付/票务接口；PD-026 高级活动日历/提醒明确不进入 1.0。

### W10 · 发布门槛与回归测试

**验收门槛**：
- [ ] 用户需求与设计冲突项已复核；未裁定功能没有危险默认值。
- [ ] `npm run check` 与 Taro 生产构建通过，CI 与适配脚手架状态有实测记录。
- [ ] 微信开发者工具与真机：地图、面板层级、定位拒绝、图片、键盘、安全区与四栏导航可用。
- [ ] 未登录公开浏览可用；个人操作登录引导清楚；私人信息越权测试为零暴露。
- [ ] 日记创建—补充—关联—时间轴—重启—离线—同步形成完整闭环。
- [ ] 城市/酒吧数据来源真实，失效营业状态、未知坐标、不可访问外链不会误导。
- [ ] 隐私说明、用户协议、内容授权、举报审核、注销/删除与必要的平台合规步骤完成。
- [ ] 回滚方案、备份/恢复、监控、错误响应、图片和日志保留政策有记录。

## 5. 不可跳过的迁移与兼容测试

1. `miniprogram/` 仍保留旧微信客户端；新 Taro 端不能因重构就删除旧版用户本机收藏、浏览、配方和主题偏好。迁移脚本必须幂等并允许回退。
2. 将旧版原生 `editorial` 默认迁移为新 A 目标，不得悄悄把开发版旧 A `#903F59` 用作正式新主题。已有手动选择其他主题的用户如何处理，需要明确迁移政策。
3. 旧的 Sites `bars/recipes/posts/favorites` 结构与新的 `drink_entries/visit_sessions/cocktails/recipe_variants` **不能直接视为兼容同一 Schema**；需要版本化 API 和数据迁移计划。
4. 微信小程序的 `map` 控件要真机验证覆盖层；任何无法保证手势的设备应有显式「展开/收起」「查看列表」入口。
5. 正式端不出现“调试同步地址”“设备令牌”“管理员登录”等工程控件，也不把虚构界面样例酒店写入实际地图数据。

## 6. 暂不在首轮实现、需另外确认或后移的项目

- 地图面板首次展示高度；全局「＋」最终五项菜单合并方式；「我的」默认网格还是时间轴。
- 原 UI-003 默认公开打卡与快速星级自动发表，除非专门重新裁定，否则不可启用。
- 活动高级日历/收藏/关注/提醒订阅（PD-026，已明确延期 1.0 之后）。
- 大规模个性化推荐、自动 AI 创作、复杂榜单排序、自动商家广告投放、支付/票务、直播与私信。
- 完整四端同时交付；本批首先准备微信小程序，其余平台按真实开发资源安排。

## 7. 开发任务的「完成」定义

**文档完成**：规范已合并到 GitHub，含已确认与待定标记。  
**代码完成**：功能在 Taro 工程可复现、通过检查与单测。  
**微信功能完成**：微信开发者工具 + 对应真实设备验收通过。  
**可以公开发布**：正式认证、数据权限、内容治理、备案合规、隐私、备份与回滚均满足上线门槛。

这四个状态不能混用。当前提交仅完成第一项——文档与开发准备。
