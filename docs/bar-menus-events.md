# 酒迹 · 酒单与活动模块设计（PD-023～026）

状态：产品目标与交付分期已确认，业务 API、商家后台、活动通知与支付均**未据此完成开发**。

## 1. 酒单与酒款双向关联（PD-023）

### 初期 C：结构化酒单
认证酒吧经营者可维护酒单条目：名称、品类、价格与币种、说明、图片、供应状态及更新日期。可以关联 `cocktail_id`，但**不应自动断言酒吧实际使用的配方版本与酒迹知识库的某个 recipe_variant 相同**。

- 酒吧详情 → 酒单条目 → 酒迹酒款简介与可浏览的公开配方版本。
- 酒款详情 → 有证据表明供应该酒款的酒吧列表；可结合 PD-007 的地图搜索，只有经过核实的酒吧坐标才允许精确地图落点。
- 特色酒款无法可靠匹配时可以保持未关联，允许授权店主或用户提供候选匹配，由审核确认。
- 供应、价格、营业时间具有时效性，需要注明更新日期、来源；不能让过期菜单信息持续被展示为实时供应。
- 酒单图片/PDF 可以作为辅助资料，但结构化条目是搜索筛选和跨模块关联的基础；不因为用户投稿就自动认定为商家官方酒单。

### 后期 D（目标，不作为初期承诺）
发展酒吧原创特调、调酒师作品档案与署名、季节性酒单、历史菜单版本、经合法授权公开的专属配方和可能的饮品评价。作者许可、配方发布与关联遵守 PD-012，不从未公开的商家材料猜测配方比例。

## 2. 预约信息与活动展示（PD-024）

**1.0 范围：**酒吧资料和活动页显示经核实的官方预约电话、外部预约链接、外部活动报名入口；不在酒迹内生成有效预订订单、实时空位、候补或票务交易。

活动基本记录包含：主题、举办酒吧、主办方、开始/结束时间（带时区）、地点、活动描述、宣传图、对外联系方式/报名 URL、来源、验证状态、取消/变更状态与更新时间。

- 即将举办列表只展示尚未结束且状态可用的活动；已结束或取消不应仍显示为「即将举办」。
- 外部链接由实际商家/主办方提供或可验证的可靠资料支持，不编造预订 URL、票价、名额或空位。
- 微信等平台上的外链打开方式应依据平台限制进行适配；无法跳转时提供经过验证的备用联系方式。
- 活动包含酒精相关宣传时需遵守适用的广告、年龄与内容规范，营销内容清楚标识。

## 3. 官方发布与社区纠错（PD-025）

- **认证商家**：可建立、修改、取消自己酒吧的官方活动，官方身份需和酒吧控制权绑定。
- **普通登录用户**：可提交活动线索、照片和纠错证据；先进入候选/待核实队列，不直接冒充官方活动。经 AI 辅助审核与必要人工复核后发布，展示实际来源和核实状态。
- 合并重复活动须有规则（酒吧、名称、时间、主办方），不能凭名称相近就覆盖真正不同的场次。
- 编辑与撤销应留痕；当官方活动与用户线索冲突时记录来源证据、优先核验并允许申诉。
- 活动取消或时间改变时及时更新信息，不承诺未上线的实时通知机制。

## 4. 活动发现与提醒——**全部延期至 1.0 之后**（PD-026）

确认的完整 D 愿景：活动日历、按日期/活动类型筛选、活动收藏、开始提醒、关注酒吧、关注酒吧的活动动态，以及由用户自行选择的活动更新订阅通知。

**首个 1.0 不交付上述 PD-026 高级发现与通知功能。** 1.0 仍提供 PD-024/025 已确定的基本酒吧活动信息列表/详情及有效外部预约和活动报名入口。不能将 PD-026 延后解读成删除酒吧活动展示。

后续开发需：
- 用户登录后建立活动收藏与酒吧关注关系；此处的「关注酒吧」与 PD-009 的「关注用户」是两种不同关系。
- 自愿开启提醒、确认推送渠道与提前量；用户随时关闭订阅及撤销通知权限。
- 遵守微信小程序订阅消息、iOS/Android/HarmonyOS 原生通知及权限规则，不默认推送、不假装已授予通知权限。
- 区分活动日历和外部报名/售票，通知不能声称完成预约。
- 设计提醒去重、时区、活动改期、取消、链接失效、活动过期与消息隐私保护。
- 即便后续启用「活动收藏」，它也不会自动意味着拥有平台内部票务或预订订单。

## 5. 实体与 API 草案（未部署）

```text
bar_menu_items(
  id, bar_id, title, description, menu_category,
  price_amount_nullable, currency_nullable, available_status,
  cocktail_id_nullable, image_id_nullable, source_kind,
  source_ref, observed_at, verified_at_nullable, updated_at
)
bar_activities(
  id, bar_id, title, organizer_id_nullable, description, image_id_nullable,
  starts_at, ends_at, timezone, status, location_note,
  booking_url_nullable, booking_phone_nullable,
  source_kind, source_ref, verification_status, created_by, updated_at
)
activity_change_requests(
  id, activity_id_nullable, bar_id, submitted_by,
  proposed_fields, evidence_refs, moderation_status, reviewed_by
)
```

建议将商家声明 / 用户线索 / 管理员核实区分为状态，且使用不可删除审计版本处理修改与争议；不得让游客直写商家官方内容。

后续阶段才引入 `activity_favorites`、`bar_follows`、`notification_preferences`、`notification_jobs` 等关系，若提前建表应保证未开放的客户端入口不会造成误导。

API 方向仅作为开发讨论：`GET /v2/bars/:id/menu`、`GET /v2/bars/:id/activities`、`GET /v2/cocktails/:id/serving-bars`、`POST /v2/activities/proposals`。写接口需要普通用户/认证商家/审核员区分权限；真实部署时重新核对路径、鉴权和兼容迁移。

## 6. 1.0 验收边界

1. 认证商家可以为自己酒吧维护酒单与官方活动；不能操作其他酒吧的资料。
2. 可信的酒单条目双向链接到对应酒款；未知关联和价格显示为未核实或缺失，不猜测供应。
3. 游客能浏览已发布活动、官方外部报名/预约信息；链接无效时不能标为可预约。
4. 用户投稿活动须经审核才能公开，并注明来源；取消/过期活动退出「即将举办」。
5. 1.0 不出现虚假的订座下单、实时空位、票务、活动通知或收藏成功提示。
6. 后续阶段再独立测试收藏、订阅、通知和跨平台权限，不能把它们写入 1.0 已验收状态。
