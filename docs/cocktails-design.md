# 酒迹 · 调酒模块详细设计（草案）

## 1. 决策与目标

来源：产品决策 PD-010。**长期目标是 D「智能调酒助手」，先完成 C「调酒知识库与用户创作」**。本设计不是已完成实现的声明。酒吧标签会另行讨论，暂不擅自设定规则。

调酒模块既需要传统的知识库和个人创作，也要为“根据食材找配方、按杯子容量换算、按味道挑酒、用喜欢/不喜欢手势学习偏好”提供一条清晰的演进路径。

## 2. 用户体验与页面草案

### 酒款首页与查找
- 搜索酒款名称、别名、基酒、配料和标签；按酒款显示候选，不把多个同款版本在默认结果里变成无序重复卡片。
- 显示酒款代表图、简介、标签和版本数量；酒款详情下列出多个配方版本。
- 支持查看不同版本作者、配料、步骤、技术难度、出品量、成品图和用户评价。

### 个人创作与评分
- 登录后创建配方（新酒款或现有酒款的新版本）、草稿、编辑已拥有的版本、上传照片、申请公开；公共内容按 AI 辅助及人工升级的审核流程处理。
- 在具体版本的详情页评分、评价和分享；不同版本拥有独立作者和来源信息。
- 允许保留私密配方、草稿和编辑历史，身份与可见性执行 PD-003 / PD-006；合并账号后的归属变更记录不得丢失。
- 依据已确认的 PD-011，用户评分**只归属具体配方版本**；酒款主页汇总展示公开有效版本的评价表现，清楚标记为“版本评分汇总参考”，而不是独立酒款评分。汇总统计方式与最低样本量尚待确定。

### 材料库存与“我能调什么”
- 用户可以选择或录入手边的基酒、利口酒、果汁、糖浆、苦精、气泡水、装饰材料等。
- 结果分为「现有材料足够」「还缺少材料」「替代建议（需核实）」；可选装饰不应与必需材料同等计入匹配度。
- 材料名称与别名规范化；可匹配品类但仍需核验具体商品是否适用。
- 库存是否由用户长期保存、是否记录数量和保质期、替代程度及短缺容忍值尚未确定。

### 杯型与容量调节
- 用户选择杯型（如马天尼杯、古典杯、高球杯、库佩杯）及杯子标称容量，设置目标出品量、份数或目标总液体量。
- 对有标准用量的材料可按比例给出参考量；对摇和造成的稀释、杯内冰块占用、碳酸/奶泡补足、分层以及 garnish 给出独立估算或提示。
- 杯型建议是体验辅助，不要求每款酒都能准确填满不同杯型；过小或不合理目标量应警示。
- 精确算法、默认杯型容量及是否支持单位换算（ml / oz）尚待细化。

### 口味偏好与卡片推荐
- 按酸甜苦、烈度、口感、基酒、场景、现有材料与用户排除项筛选或推荐酒款。
- 第一阶段可用规则与标签排序，展示推荐原因（例如“有全部材料”“偏酸”“低酒精度”）；后续才考虑 AI 模型学习。
- 远期提供卡片式「喜欢 / 不喜欢」反馈，用户设想**左滑喜欢、右滑不喜欢**。方向属待交互验证的设计意向，推荐 UI 同时提供明显的按钮、无障碍可点击操作和撤销入口。
- 反馈是偏好而不是公开酒款评分；用户撤销/清除偏好后系统需相应更新推荐，不把私人喜好泄露给其他账号。

这些是用于讨论的概念实体，不是现行 Cloudflare D1 已存在的表。标签复用的是**标签服务机制**，而不是将“酒款标签”和“酒吧标签”未经审核地混合使用。

标签体系已在 PD-013 确认为**客观属性与主观体验双层**：例如配方中的材料与技法应依据版本数据核实，「清爽」「偏酸」等主观体验则通过用户评价、投票及审核逐步形成共识。酒款与酒吧使用不同分类，详细治理流程见 [标签系统方案](tags-design.md)。

### 概念层级（以经典玛格丽特为示例）
```text
酒款：Margarita / 玛格丽特
 ├─ 配方版本 A：经典龙舌兰 + 橙味利口酒 + 青柠
 ├─ 配方版本 B：作者的糖浆调整版
 └─ 配方版本 C：其他创作者的改良版

每个版本
 ├─ 配料行（可用于匹配材料和计算容量）
 ├─ 制作步骤、杯型、图片
 ├─ 独立的公开/私密状态
 ├─ 用户评价与评分（只属于该配方版本）
 └─ 修改历史（不等于新增版本）
```

## 3.1 评分归属与酒款页面统计（PD-011 已确认）

- 已确认：配方版本 ID 是用户评分的唯一评价对象；酒款 ID 只用于配方归组与汇总展示。
- 酒款主页展示可核验的汇总参考，例如公开版本数量、各版本有效评分、有效评价总量、版本分布、热门版本，并明确说明“依据该酒款下的配方版本评分整理”。
- 只纳入经审核可见的版本评分；撤回、违规或私密内容不得在公众汇总中泄露。汇总计算必须与公开版本的有效评价口径一致。
- **不能将所有配方的评分简单平均后直接称为“酒款官方评分”**，尤其应避免只有少量评价的版本与大量评价的版本在无说明下等权造成误导。
- 样本过少要显示“暂无足够评价”；具体阈值、统计修正方法、评分量纲和缓存刷新机制仍未决。
- 商业投放不能改变客观聚合排名，评价可申诉并接受 AI 辅助与人工复核的内容治理。

## 3.2 改编溯源与协作修改（PD-012 已确认）

配方创作有三种不同的业务行为。第一种是独立投稿：用户为一款酒提交自己的版本。第二种是改编版本：在新配方中记录被改编版本的 ID、作者、来源链接与改动说明，形成可追溯的关联，不改写原版本。第三种是协作修改：用户给已有版本提出修改建议，须经原作者或授权维护者采纳后，才进入该版本的修订历史。

建议数据结构增加：

```text
recipe_variants.derived_from_variant_id
recipe_variants.derivation_note
recipe_change_proposals(
  id, target_variant_id, proposer_user_id, diff_payload,
  reason, status, reviewer_user_id, reviewed_at
)
recipe_contributions(
  id, variant_id, contributor_user_id, contribution_kind,
  proposal_id, revision_id, recorded_at
)
```

界面应区分原作者、改编者、提议者、采纳者，显示来源链接及变更记录。被改编配方和新配方独立保存评价。协作提议不能直接覆盖别人作品。

需遵循作者署名、内容许可及审核流程。引用配方思路不表示获得复制原图片、独创说明等内容的许可。改编许可、作者撤稿时如何处理关联、多人维护的权限边界属于待定事项。本节是设计方案，并非已实施数据库迁移或审核工作流。

## 4. 与当前实现的差异

目前 `packages/contracts/schemas/recipe.schema.json` 仅要求 `id`、`title`、`ingredients`（字符串）、`steps`（字符串）、`visibility`，微信调酒页 `apps/wechat/src/pages/mix/index.tsx` 仍主要是简单的配方录入、展示和复制。

下一步需要先做**兼容性数据迁移**：为历史配方生成或关联 `cocktail_id`；将字符串材料解析/人工确认成结构化配料行；对无法解析的材料保留原文，不编造 ml、酒精度或配方出处。不要破坏已发布的同步协议；可以新建版本化 API，或在经过测试的兼容迁移后逐步切换。

## 5. 分阶段建议与验收

| 阶段 | 建议重点 | 验收思路 |
| --- | --- | --- |
| C-1：知识库与创作 | 酒款目录、多版本、各版本详情、编辑与草稿、用户发布及评分、酒款标签 | 一款酒有多个版本且作者不互相覆盖；可以评价、审核、撤销与查询 |
| C-2：规则辅助调酒 | 材料清单过滤、基础杯型及容量换算、口味标签筛选/规则推荐 | 对不齐材料/可选配料有正确区分；按杯型调整用量且提示不适合精确缩放的情况 |
| D：智能体验 | 滑卡喜好反馈、跨设备偏好、AI 创作/替代/个性化推荐 | 推荐理由可解释；偏好可撤销；AI 输出有安全评估、来源说明与人工上报机制 |

**上表为开发建议而非强制的产品阶段范围。** 已确定的是「C 先、D 后」及所有目标能力，不代表用户已确认 C-1/C-2/D 的精确交付期限。

## 6. 待进一步确认

1. 具体评分制、最低样本量、跨版本评价去重和汇总算法（PD-011 已确认评分归属）。
2. 酒款名称规范、改编许可、作者署名与协作维护者权限（已确认允许改编并保留来源及贡献）。
3. 杯型容量的单位、默认容量、是否扣除冰块占用。
4. 库存记录是否持久保存、是否记录数量和是否允许自定义材料。
5. 口味推荐是否可按酒精度/过敏排除、无酒精是否独立筛选。
6. “左滑喜欢、右滑不喜欢”最终是否符合目标用户习惯。
7. 酒款标签分类与管理规则；酒吧标签将单独讨论。
